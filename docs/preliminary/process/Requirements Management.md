# Continuous Requirements Management

Requirements Management spans Preliminary and A–H; it is not a final sequential
phase or an additional canonical storage layer.

- Preserve each originating stakeholder/system signal in the adopting project's
  ingest channel. The signal is evidence, not itself a canonical Requirement.
- Define each mandatory property once as a Motivation Requirement with a stable
  type-local number, Description, Evidence and Relationships. Constraints are
  expressed as requirements or principles according to scope, not a separate
  invented concrete Constraint element.
- Trace the Requirement to its stakeholder intent, drivers/goals/principles and
  affected architecture. Satisfying concepts realize Requirements using the
  permitted connector rules; do not replace typed traces with a local checklist.
- B–D define relevant Business, Application/data and Technology contracts with
  upstream traces. E verifies realization coverage/consistency/feasibility; F
  associates Work Packages with every relevant implementation and test target.
- G delivers implementation and reverse-delivers code, test and runtime evidence
  to the owning layer articles. H evaluates Assessment criteria; missing evidence
  is unmeasured, never a fabricated passing result.
- Changed requirements reopen affected prerequisite gates and dependent work only.
  Preserve history, stable phase-owned Questions/Concerns and explicit impact
  decisions. A branch merge neither verifies a requirement nor closes a gate.
