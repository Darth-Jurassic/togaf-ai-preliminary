# Preliminary 0002: Align Architecture Work with Lean Software Product Development

- Record: Reusable policy
- Tags: preliminary, lean, software-product-development, architecture-process, learning-loop, decision-control

## Context

[Preliminary 0001](0001-describe-product-context.md) requires an explicit adopter
context. The architecture process must help that project learn from product and
technology signals, delivery pain and decision-control concerns.

The core preliminary question is therefore not which architecture framework to
use first. The core question is what kind of architecture capability the
repository must support.

Architecture work should behave as part of a lean software product
development process: make evidence visible, preserve original signals, reduce
waste, expose trade-offs, validate learning with stakeholders, and convert
validated learning into product goals, constraints, options, decisions, and
improvement work.

## Decision

We will align architecture work with lean software product development.

Architecture work must support an explicit learning loop from product and
technology feedback into product learning, product decisions, delivery
improvements, and technology improvement work. Architecture artifacts are not
valuable only because they are complete; they are valuable when they improve
product learning, reduce avoidable loss, and help the organization make better
product and technology decisions.

This preliminary record is the senior process decision. Later preliminary
decisions select methods, workflow, notation, report structure, and scope
because they satisfy the process requirements defined here.

## Process Requirements

The architecture process must satisfy these requirements:

- Preserve raw feedback and source context before interpretation.
- Trace feedback, ideas, risks, and problems into stakeholders, categories,
  learning records, product goals, constraints, options, and decisions.
- Provide clear ways to streamline product-related information into learning
  loop inputs.
- Convert validated learning into product goals, measurable outcomes,
  constraints, options, decisions, experiments, and improvement work.
- Make the lean loss of ignored signals explicit enough to compare reports and
  explain priority.
- Allow goals, constraints, options, and decisions to be revisited when product
  learning changes the evidence base.
- Involve accountable stakeholder roles in validation before reports become
  committed product or technology work.
- Keep architecture artifacts lightweight, versionable, reviewable, and suitable
  for iteration.
- Support decision control by checking evidence, traceability, decision quality,
  and learning status rather than document completeness alone.

## Consequences

- Architecture framework selection must be judged by how well each framework
  supports the lean software product learning loop and decision-control
  requirements above.
- Method, notation, and tooling choices are subordinate decisions, not the core
  premise.
- Product and technology feedback must stay connected to product learning
  because current evidence is the basis for future product and technology
  decisions.
- Preliminary decisions should be ordered from core operating philosophy to
  consequence decisions and implementation rules.
